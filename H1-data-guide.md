# Data guide: project structure and how results are stored

Written for an analyst (human or agent) who did not run these experiments. It describes
the layout, the exact schema of every file, the semantics of each field, and the traps
that will produce wrong numbers if ignored. Facts here were read off the committed files
on 2 Sep 2026, not from memory.

Related documents: `H1-assignment-transcript.md` (the assignment, verbatim),
`H1-critique-and-build.md` (analysis and experimental design), `CLAUDE.md` (decisions log).

---

## 1. The one invariant that governs everything

**No LLM output enters the ground truth, the grading, or the statistics.** Queries and
gold answers are generated by `src/generate.py` from a committed seed; every Task 2
answer is computed twice — once via `decimal.Decimal` with `ROUND_HALF_UP`, once via
`fractions.Fraction` — and asserted equal. The only LLM-produced values anywhere are the
`raw` strings in the run files.

If you write analysis code, keep this true:

- Never recompute a gold answer with float division. `round(a/b, 8)` accumulates float
  error, and Python's built-in `round()` is banker's rounding, not the round-half-up the
  gold uses. Read `gold` from the data files, or use `Decimal`/`Fraction`.
- Never use a model to judge, classify, or re-grade a response. Grading is already done
  and committed; see §5.
- `python3 -m src.main verify` re-derives everything from the seed and diffs it against
  the committed files. It exits non-zero on any drift. Run it before trusting anything.

## 2. Layout

```
HW1/
├── data/                     committed inputs and derived summaries (see §3)
├── runs/<model>/*.jsonl      every trial (see §4)
├── src/                      the harness
│   ├── generate.py           seeded queries + gold answers
│   ├── verify.py             re-derives and cross-checks the ground truth
│   ├── ollama.py             HTTP client for the local models
│   ├── experiment.py         the model × temp × arm × query × seed loop
│   ├── grade.py              validity, correctness, error taxonomy  ← read this first
│   ├── sweep.py              accuracy/consistency curves, inflection rule
│   ├── tokens.py             per-model tokenization stats
│   ├── report.py             graded runs -> report.html (the deliverable)
│   ├── ui.py                 graded runs -> ui.html (interactive explorer)
│   ├── main.py               CLI entry point for all of the above
│   └── utils/
│       ├── constants.py      MODEL_REGISTRY, task names, famous-fraction exclusions
│       ├── config.py         every frozen setting; the temperature grid; the sweep rule
│       ├── prompts.py        the three prompt templates, verbatim
│       └── trace.py          JSONL reader/writer — `load_all()` is the entry point
├── report.html               generated deliverable
└── ui.html                   generated explorer snapshot
```

Python 3.12+, no third-party dependencies. Nothing needs installing to read the data.

## 3. `data/` — inputs and derived summaries

### `task1_queries.json` — 10 objects

```json
{"qid": "Q1", "s": "PkUuq", "l": 5, "gold": "quUkP",
 "case_pattern": "UlUll", "n_upper": 2, "distinct_chars": 5}
```

| field | meaning |
|---|---|
| `qid` | `Q1`…`Q10`. Joins to `qid` in the run files. |
| `s` | the input string; character set is the 52 ASCII letters |
| `l` | string length — the complexity band. Q1–Q5 are `l=5`, Q6–Q10 are `l=8`. |
| `gold` | `s` reversed |
| `case_pattern` | `U`/`l` per character; every string is guaranteed mixed case |
| `n_upper`, `distinct_chars` | covariates for stratified analysis |

### `task2_queries.json` — 10 objects

```json
{"qid": "Q1", "a": 744, "b": 336, "places": 5, "gold": "2.21429",
 "expansion": "short_period", "magnitude": "A>B", "period": 6,
 "decimal_len": 1, "exact": "31/14"}
```

| field | meaning |
|---|---|
| `a`, `b` | the operands; the task is `a ÷ b` |
| `places` | decimal places to round to — the complexity band. Q1–Q5 are `5`, Q6–Q10 are `8`. |
| `gold` | `a/b` rounded half-up to `places`, always carrying exactly `places` decimals |
| `expansion` | `terminating`, `short_period` (repeat length < 10), or `long_period` (≥ 10) |
| `magnitude` | `A>B` or `A<B` — governs whether the answer has a leading integer digit |
| `period` | repeating-block length of the reduced denominator; `0` if terminating |
| `decimal_len` | digits in the exact expansion when terminating |
| `exact` | the reduced fraction, as a string |

Generation constraints, all enforced and re-checkable: `a % b != 0` (the handout requires
a non-integer result); no fraction whose exact value sits on the rounding boundary (a tie
would penalise the model for our unstated convention); no fractions with famous decimal
expansions such as `22/7` or `355/113` (a correct answer there is recall, not
arithmetic — the contamination confound this assignment is about); terminating fractions
must reach the rounding position, so no `7.70000` padded-zero queries.

Each band contains one query per stratum slot: `(short_period, A>B)`, `(short_period,
A<B)`, `(terminating, A<B)`, `(terminating, A>B)`, `(long_period, A<B)`.

### `fewshot_pool.json`

`{"task1": {"5": [...], "8": [...]}, "task2": {"5": [...], "8": [...]}}` — three
held-out examples per complexity band, same object shape as the query files. Generated
with a **different seed** (`916220` vs `6220`) and asserted disjoint from the test
queries. Shots are always drawn from the item's own band.

### `ladder_queries.json`

Supplementary wider complexity ladder: Task 1 at lengths 3, 5, 8, 12, 16, 20 (30 items);
Task 2 at 2, 5, 8, 12 places (20 items). Its `qid`s restart at `Q1` and **collide with the
main query files** — `Q1` means different things in the two sets. The collision is
handled structurally: ladder runs write to `runs/<model>/ladder/`, so they can never share
a file with a main run, and every trial carries `ladder: true`. Filter on that flag before
joining trials to query metadata.

### `models.json`

Per model alias: `full_name`, `org`, `params`, `quantization`, `url`, `ollama_tag`,
`digest`, `installed`, `defaults` (the model's own default hyperparameters as reported
by ollama), `details`. This file is the authority for model provenance — **the `digest`
field inside the run headers is `null`**, because the registry is populated at report
time rather than at run time.

### `sweep.json` — derived, regenerate with `main.py sweep`

`pooled` is a list of `[temperature, {accuracy, self_consistency, n, invalid}]` across
all models and tasks. `per_model` holds the same per `model|task|band` key. `decision`
records the curve shape, the located knee if any, and `pair` — the two temperatures
selected for the deliverable tables. Currently `flat_at_floor`, pair `[0.0, 1.0]`.

### `tokens.json`

Not generated yet. `main.py tokens` produces per-model `n_tokens` and `chars_per_token`
for each Task 1 string, measured through each model's own tokenizer.

## 4. `runs/` — the trial records

One file per experiment cell:

```
runs/<model-alias>/<task>.<arm>.t<temperature>.jsonl
runs/qwen2.5-1.5b/task1.fewshot.t1.0.jsonl
```

`model-alias` ∈ `qwen2.5-1.5b`, `gemma3-4b`. `task` ∈ `task1`, `task2`. `arm` ∈
`zeroshot`, `fewshot`, `cot`. Temperature is one of the 11 grid points 0.0…1.0.

**Line 1 is a header** (`"type": "run"`); every later line is a trial
(`"type": "trial"`). Lines are flushed as they are written, so a killed run leaves a
valid prefix — a truncated final line is possible and readers should tolerate it.

### Header fields

`model`, `task`, `arm`, `temperature`, `ollama_tag`, `digest` (null — see §3), `k`,
`ladder`, `task_name`, `prompt_version`, and the frozen settings: `seed` (the *data*
seed, 6220), `fewshot_seed`, `top_p`, `top_k`, `repeat_penalty`, `num_ctx`,
`num_predict` (keyed `task.arm`), `n_shots`, `temp_grid`, `inflection_curve`.

### Trial fields

| field | meaning |
|---|---|
| `qid` | joins to the query files |
| `seed` | **the sampler seed**, `0…k-1`. Not the data seed. Distinct draws from the same distribution. |
| `prompt` | the exact user message sent |
| `raw` | the model's unmodified response |
| `extracted` | the answer as read out of `raw`. For `cot` this is the text after the last `FINAL:`; otherwise `raw.strip()`. |
| `normalized` | `extracted` with wrapping removed (fences, quotes, markdown, a leading “The answer is:”). For Task 2 it is the parsed numeric token. |
| `gold` | copied in for convenience; identical to the query file |
| `valid` / `correct` | **strict**: computed on `extracted` |
| `valid_norm` / `correct_norm` | **normalised**: computed on `normalized` |
| `error_type` | see §5 |
| `extraction_ok` | false only when a `cot` response had no `FINAL:` marker |
| `truncated` | true when the response hit `num_predict` |
| `invalid` | `truncated or not extraction_ok` — **exclude these from denominators** |
| `done_reason` | ollama's stop reason (`stop`, `length`) |
| `prompt_tokens`, `output_tokens` | from ollama, in that model's own tokenizer |
| `wall_ms` | latency of the call |
| `n` | 1-based counter within the file |

`trace.load_all()` returns `(headers, trials)` and denormalises `model`, `task`, `arm`
and `temperature` onto every trial, so trials are self-describing after loading.

## 5. Grading

Implemented in `src/grade.py`. Two independent criteria come straight from the
assignment's Task 1 specification and are kept separate throughout:

- **valid** — `len(answer) == len(s)`. The output contract.
- **correct** — `answer == gold`. The operation.

Correctness implies validity; the reverse does not. A model that is mostly *invalid* has
an instruction-following problem; one that is mostly *valid but incorrect* has a
capability problem. These are different findings.

Every trial carries both a strict and a normalised verdict. Strict is the handout's
literal reading, under which a preamble makes a Task 1 answer invalid. Normalised strips
wrapping first. **Report both, or state which you used.** Existing analysis headlines the
normalised numbers.

### Task 1 `error_type`

`none`, `extra_text` (right answer wrapped in prose), `wrong_length`, `wrong_order`
(correct characters, wrong order — an anagram of the gold), `wrong_chars`, `empty`,
`extraction_failed`.

### Task 2 `error_type`

`none`, `format_only` (right value, wrong surface form — commas, scientific notation,
trailing zeros; scored correct after normalisation), `precision_error` (right digits,
wrong number of decimal places), `rounding_error` (correct quotient, rounded wrong at the
right position — within one unit of the last place it printed), `wrong_digits` (the
division itself is wrong), `unparseable`, `extraction_failed`.

The `wrong_digits` vs `rounding_error` split is the interesting one: a model that divides
correctly but rounds wrong has a completely different failure from one that cannot divide.

## 6. Metrics

Defined in `src/sweep.py`, computed per `(model, task, band, temperature)`.

- **accuracy** = correct ÷ valid trials. Invalid trials are excluded from the
  denominator, not counted as wrong.
- **self-consistency** = for each query, the share of its k draws equal to the modal
  draw, averaged over queries. It measures repeatability, *not* correctness: three
  identical wrong answers score 1.0.

Two properties to respect when reading consistency: it has a **floor of 1/k** (0.2 at
k=5), not 0; and it is always computed on `normalized`, so the strict/normalised choice
does not move it.

Resolution: at k=5 with 5 queries per band, each curve point rests on 25 trials —
roughly ±10pp. Read the curves as shapes. Do not claim an inflection located more
precisely than ±0.1 on the temperature axis.

The deliverable table cell is the **modal** `normalized` output across the k draws.

| qwen2.5-1.5b | task2 | zeroshot **(ladder)** | 1100 | 11 | 5 |

The coverage is deliberately asymmetric and the gaps are not random:

- **Only Qwen has few-shot and CoT.** Any prompting comparison is single-model. Do not
  attribute a prompting effect to models in general from this data.
- **Task 2 CoT is the exception cell**: two temperatures, and k=1 at t=0.0. Rates are
  still meaningful; counts are not comparable to other cells without normalising.
- **The third model (`mistral:7b`) was never pulled.** The assignment requires three
  LLMs; two exist. This is a known, open gap.
- **Ladder runs exist for Qwen only, zero-shot only.** They live in
  `runs/<model>/ladder/`, carry `"ladder": true` in the header and on every trial, and
  cover Task 1 at lengths 3/5/8/12/16/20 and Task 2 at 2/5/8/12 decimal places, with 5
  queries per band. Gemma has no ladder runs.

## 8. Established results, so they are not re-derived

Verified against the committed files; re-check anything you intend to publish.

- Accuracy is at floor nearly everywhere. Pooled zero-shot accuracy across both models
  peaks at 0.045. `sweep.py` classifies the pooled curve `flat_at_floor` (range 0.03) and
  the pre-registered rule selected temperatures **0.0 and 1.0** for the tables.
- Self-consistency degrades cleanly everywhere, pooled 0.99 → 0.33 across the grid, and
  carries essentially all the signal in this dataset. Temperature demonstrably changes
  behaviour even where it cannot change correctness.
- At t=0.0 all draws are identical, confirming greedy decoding is deterministic here.
  This was verified rather than assumed.
- **Gemma 3 4B, task1 l=5** is the only non-floor zero-shot cell: 0.20 at t=0.0, peaking
  at 0.32 across t=0.2–0.6, falling to 0.12 at t=1.0. Note it is *non-monotone* — mild
  sampling beats greedy here.
- **Few-shot on Qwen task1** is the only arm with a monotone accuracy decline
  (0.11 → 0.00). Validity rises 0.10 → 0.78 at greedy while accuracy rises only
  0.00 → 0.11: three examples teach the output contract far more effectively than they
  teach reversal.
- **CoT costs validity and buys nothing measurable**: 54 invalid trials of 604 (~9%,
  versus 0% zero-shot), no accuracy gain. Its apparent hump around t=0.3 is within noise
  at this resolution.
- Task 2 validity is 1.00 in every arm and at every temperature — every Task 2 failure is
  arithmetic, never formatting. `wrong_digits` is the dominant error type overall (1,687).
- Task 2 accuracy is 0.00 for both models at every temperature and in every arm, on the
  main queries.
- **Ladder, Task 1**: exactly one correct answer in 1,650 trials (l=3, t=0.8). Zero at
  every length from 3 to 20 and at every temperature. The reversal failure is not a
  complexity effect for this model — it fails at the shortest setting available.
- **Ladder, Task 2**: the capability edge sits between 5 and 8 decimal places. Non-zero
  accuracy at 2 dp (0.00 → 0.20, *rising* with temperature) and 5 dp (0.20 → 0.12,
  falling); exactly 0.00 at 8 and 12 dp at every temperature. The rising 2 dp curve is
  unexplained: the hypothesis that greedy decoding locks into a systematic decimal-point
  error accounts for only ~8% of the failures there. Treat it as an open observation on
  25 trials per cell, not a mechanism.
- At 8 and 12 decimal places roughly a quarter of wrong answers are magnitude errors
  (right-ish digits at the wrong power of ten), versus ~8% at 2 dp.
- Case sensitivity does not explain the Task 1 failures: grading case-insensitively moves
  ladder l=3 from 0.00 to 0.07 and nothing else. The one exception is the CoT arm on the
  main queries, 0.032 → 0.079.

## 9. Loading the data

```python
import sys; sys.path.insert(0, ".")          # run from the HW1 directory
from src.utils import trace
from src import generate, sweep

headers, trials = trace.load_all()            # every run file, denormalised
q1 = {q["qid"]: q for q in generate.load("task1_queries")}

valid = [t for t in trials if not t["invalid"]]        # ALWAYS filter first
zs    = [t for t in valid if t["arm"] == "zeroshot"]
acc   = sum(t["correct_norm"] for t in zs) / len(zs)

cells  = sweep.cells(trials, arm="zeroshot")           # keyed (model, task, band, temp)
series = sweep.curve(cells, model="gemma3-4b", task="task1", band=5)
shape  = sweep.shape(series)                           # knee / monotone / flat_at_floor
```

Or read the JSONL directly — one JSON object per line, first line is the header, no
dependencies required.

## 10. Traps, collected

1. Not filtering `invalid` inflates the error count and shrinks accuracy.
2. Mixing `correct` (strict) and `correct_norm` (normalised) across an analysis.
3. Assuming uniform k — `task2.cot.t0.0` has k=1.
4. Joining ladder `qid`s to main query `qid`s; they collide (`Q1` exists in both and
   means different queries). Every trial carries a `ladder` boolean — filter on it. The
   run files themselves are already kept apart under `runs/<model>/ladder/`.
5. Reading `digest` from a run header; it is null. Use `data/models.json`.
6. Treating self-consistency as accuracy, or forgetting its 1/k floor.
7. Recomputing Task 2 gold with float division or Python's banker's `round()`.
8. Comparing prompting arms across models — only Qwen has all three.
9. Reading a trend into differences smaller than ~10pp at k=5.
